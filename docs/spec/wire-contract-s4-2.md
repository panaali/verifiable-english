## 0. Scope, one paragraph

Rust has no contract engine. Item 2 gives it one that runs the same generated tables as Lean and Python read,
so that the base contracts of items 3 to 6 have a Rust column and Rust stops hand-mirroring Lean's fault order.
Rust stays untrusted (docs/ARCHITECTURE-REVIEW-2026-10.md:44): its engine decides no verdict, reads only
generated tables, and its outcome is compared with Lean's, never trusted alone. Nothing here changes a verdict,
an identity, a code, a contract, a Lean file, a response schema or an output of any program, except the
`error` object of section 6, which changes in wc-s4-2b and not before.

## 1. Definitions, by reference

The definitions of base spec 2.1 to 2.8 apply to Rust unchanged: values, the root, pointers and patterns (2.1,
with `*` over an object in code point order of the keys), the files (2.2), entries, guards and type forms
(2.3), the T1 kinds (2.4), hooks, classifiers, views and adapters (2.5), expansion and its order (2.6), the
record (2.7) and the outcomes with the overlay (2.8). The engine corpus is base spec 8.1, unchanged:
`conformance/wire-contract/engine.json` and its records `conformance/wire-contract/engine-golden.json`. This
spec states no new definition of any of them; where it says "record", "outcome" or "instance", it means the
base spec's.

## 3. The table types

`rust/ve-kernel/src/contract.rs` holds one Rust type per type of `lean/VE/WireContract/Table.lean`, with the
same constructors and fields in the same order: `Step`, `Base`, `Pattern`, `Value`, `Atom`, `TypeForm`, `Lit`
(the guards), `NameClass`, `Renderer`, `Piece`, `Member`, `Kind` (the T1 kinds of base spec 2.4, `hook` and
`classifier`), `Check`, `Entry` (check, `each` group, and the resolved include `scope` with its view and its `as`
code), `Phase` and `Table`; plus `Source`, a file the module was generated from with its revision and SHA-256.
Every string is `&'static str` and every list a `&'static [T]`, so a generated table is a static value that the
compiler type-checks. As in Lean, a limit is written as its numeral, a name class is written out, every code
carries its class, and every template is split into pieces (base spec 5.1). The types hold data only and have no
`impl` beyond derived traits; the engine of wc-s4-2b is a set of functions over them.

## 4. The grammar of a generated Rust table module

A generated module (`contract_tables.rs`, and the corpus tables of section 5) is, in this order, and nothing
else:

1. a header of line comments that begins `// GENERATED by tools/wire_contract.py`, names the directory it was
   generated from and each file of `SOURCES` with its revision and SHA-256, and ends `Do not edit.`;
2. one `use` of the table types: `use crate::contract::*;` in the kernel, `use ve_kernel::contract::*;` in the
   corpus tables;
3. `pub static SOURCES: &[Source] = &[…];`: `limits.json`, `names.json`, then every contract of the module, in
   code point order of the file name;
4. one `pub static <UNIT>: Table = Table { … };` per contract, in code point order of the unit; `<UNIT>` is
   the unit's name before `@`, upper case, with `-` written `_` (`soft-norms@0` is `SOFT_NORMS`);
5. `pub static TABLES: &[&Table] = &[&<UNIT>, …];` in the same order.

A value in 3 to 5 is built from struct and enum literals of the types of section 3, `Some`/`None`, tuples,
`&[…]` slices, string literals, integer literals, `true`, `false`, and `&<UNIT>` in 5. There is no `fn`, no
`impl`, no macro, no attribute, no `unsafe`, no `mod`, no `const` expression other than a literal, and no
recursion. A string literal escapes `\`, `"` and every character below U+0020 or equal to U+007F (as
`\u{…}`) and writes every other character as itself. Lists that the base spec reads as sets of keys (`keys`'
`required` and `optional`, `exact_keys`' `keys`) and the names of a check's `args` are emitted in Unicode code
point order (base spec 2.1), not UTF-16 order; every other list keeps the contract's order. An include is
resolved as in Lean: its entries are inlined in a `Scope`.

**Bound to its source.** `tools/wire_contract.py --check` regenerates the module and fails with `WC11` when the
committed file differs, as it does for the Lean modules (base plan 3.1 item 2). A cargo test
(`rust/ve-kernel/tests/contract_tables.rs`) compares every `SOURCES` row with the lock it came from:
`ve/wire_contract/contracts.lock` for `contract_tables.rs`, `conformance/wire-contract/contracts/contracts.lock`
for the corpus tables. A row whose revision or SHA-256 differs from its lock entry fails, so a contract edited
and locked without regeneration fails `cargo test` as well as `--check`.

**No build script.** The tables are committed (base plan 3, table row 4); there is no `build.rs`, so the
reproducible build of `tools/rust_build.py` and `lean/checkers.lock` are unchanged in method. When the release
binary's hash moves, `lean/checkers.lock` is regenerated with the other generated files.

## 5. Where the engine-corpus tables go

The contracts of base spec 8.1 (`inner@0`, `demo@0`, `defer@0`, and `mid@0`, `forms@0` added since) are test
data. Their tables go to `rust/ve-kernel/tests/corpus_tables/mod.rs`, a module of the kernel's integration
tests, not to the product crate's source. They are emitted for every contract of
`conformance/wire-contract/contracts/`; that directory also holds `keys@0`, a contract read by the generator
tests only, whose key lists carry keys outside the BMP (U+1F600) beside keys above U+E000 (U+FF5A), where code
point order and UTF-16 order differ.

## 6. The `error` object

Rust's `Error` (`rust/ve-kernel/src/lib.rs`) gains one member, `diagnostic`, as base plan 2.5 and plan section 3
row b state. It is serialised only when it is set (`skip_serializing_if = "Option::is_none"`); `code`, `message`
and `span` are kept, unchanged, until the per-profile switch of base plan 5.1 step 6. Its value is the reported
record of base spec 2.8: the fault record, the residual record or the deferred record. `ve/backends/rust_schema/jsonl.json`
gains the optional member `diagnostic` under `$defs/error/properties/error`, typed as the three records, in the
same commit that first sets it. That commit belongs to wc-s4-2b; wc-s4-2 changes neither the error nor the
schema.

## 7. Outcomes

The Rust engine returns `fault(record)`, `clean` or `deferred(id)` (base spec 2.8). It defers on every hook,
classifier and view it lacks; for `soft-norms@0` that is every hook, classifier and view of the contract, so on
that unit Rust reports a fault only when a T1 check fails before the first of them. A deferred outcome is
counted under Rust's deferred share and never compared (plan section 3, row d); a fault or `clean` is compared
with Lean's and Python's records byte for byte. A Rust record is never the answer on its own: the overlay asks
Lean, or reports the deferred record (base spec 2.8).

## 8. What is not claimed

- That the Rust engine is correct: it is an untrusted accelerator, checked by comparison only, on the engine
  corpus and the gate's corpus.
- Any order, wording or limit owned elsewhere: every check, its position, code, class, text and limit comes from
  the generated table, which comes from the contract; Rust owns none of them.
- Any Rust hook. wc-s4-2 and wc-s4-2b add none; items 3 to 6 add Rust hooks beside each decoder.
- Any change of a verdict, of the bytes of a pilot, or of a public message: this item has none.
