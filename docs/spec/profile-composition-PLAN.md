## 1. What this plan builds

It replaces the refusal matrix that no plan states (PLANS-INDEX C4, C12) with a **composition contract**. Every
profile's row in AR-10's table declares how it takes part in a composed document (its interface).

Structural laws, **well-formedness and name freshness**, hold for every pipeline, but they make nothing sound. An
admitted route rests on typed statements about that route:
- each rewriter's own faithfulness theorem;
- an ordered pipeline theorem for each listed stack;
- a theorem that the document mode runs that pipeline.

A **matrix** computed from AR-10's rows gives every admitted list its route statement, and every refused list its
English abstention. A list with two or more rewriters whose stack is not listed is refused. On the way it lifts
the refusals that the pilots measured:

- `judgments@0` beside the soft chain;
- the soft and rights chains with `norm-defaults@0` and `readings@1` in `ve document check`;
- `judgments@0` beside `scope@0`;
- `acts@0` beside soft-norms and rights;
- discourse beside scope and acts;
- from the 2026-10-29 fidelity pilot (pc-fid-rev, section 15): `commitments@0` beside `judgments@0` (the record rule),
  discourse beside readings, and stacks of any number of rewriters whose pairs are listed; and, once another family's
  item lands, acts beside readings, a governor's own reading set beside readings, and attitudes beside judgments;
- from the 2026-10-30 re-pilot (pc-fid-rev2, section 16): writing rules for a coupled set whose candidates differ on
  more than one axis, an act phrase with several derivations inside a candidate and a purpose clause's two readings;
  and, once modality's MD-4a lands, the scenario slot in a candidate's guard (PC-12).

It schedules composition's own S2b and S4 as composition-PLAN designs them. Before weighing is built, it keeps
priority as two typed graphs, each with its owner's check, and gives "no exception" one owner (defeasible). It
tests, before building anything, whether a judged term should become a named decider premise. If so, judgment-terms
builds it in JT-4.

### 2.3 The contract, as statements (built in PC-3)

The exact statements are the specification's sections 1.2 to 1.7. They are summarised here.

- **The interface** is the field `ProfileRow.interface` (2.2). Its slot agreement (C1), its uniqueness per profile
  (C2) and its distinct ranks (C3) are proved by `decide`. Draft 1's `Step` type, `interfaces` list and C0 are
  deleted.
- **The stack order** is `stackOf`, a sort of AR-10's rows by rank. `pipelineOf` takes its order from it and from
  nothing else.
- **G2, well-formedness and name freshness** (renamed; not a soundness claim): `Rewriter.Laws`, `pipeline_preserves`,
  `pipeline_off`, `pipeline_names`. A rewriter that negates every claim can satisfy these laws, so G2 admits
  nothing.
- **Typed route evidence.** `RouteFacts s` is a proposition per listed stack `s`, and `listedStacks` the stacks the
  document mode admits. `listed_evidence` proves `RouteFacts` for each listed stack. Each listed stack's entry is
  the conjunction of these, each written out as a `Prop` (specification 1.5):
  - each rewriter's own faithfulness and its semantic preservation (`ScopeFaithful`, `ScopePreserves`,
    `ScopeSetsFaithful`; `ActsFaithful`, `ActsPreserves`; PC-7b's `DiscourseFaithful`, `DiscoursePreserves`);
  - an ordered pipeline theorem for the whole stack (the constitution set `soft + judgments + scope + acts`
    included, as `ActsScopeRuns`, with its `SplitMap` conjunct `SplitReach`, proved and listed by PC-6b; PC-7b's
    `DiscourseScopeRuns` and `DiscourseActsRuns`);
  - a theorem tying the document mode's run to `pipeline` (scope's instance, `checkDocSets_pipeline`, from
    `scope_admission_sets`).

  A run statement alone is not evidence: an entry that refuses every case satisfies it (`refuseAll_runs`).
- **Any number of rewriters (pc-fid-rev, PC-4b; specification 1.5).** A stack with no entry of its own has one
  generic clause of `RouteFacts`: the whole stack's ordered pipeline theorem (`StackRuns s`, one theorem for every
  stack, `stackRuns_all`), each rewriter's own facts (`RewriterFacts`, SUPERPOSE's being main's `superpose_faithful`),
  and the interaction lemma of every pair at positions `i < j` (`PairFacts`), not only adjacent pairs: a rewriter reads
  what every earlier one wrote. A stack of three or more is still listed by a batch (the listing rule: the batch that
  lists a stack's last pair lists the stack, with `stack_evidence`), so pairs alone admit nothing and E1s stands.
- **The record rule (pc-fid-rev, PC-4; specification 3.4).** An `.outside` profile on a slot that is no route head
  (`commitments@0`, its own mode) is a document record in the document mode: every decoder reads the environment
  without it and no decoder reads its block (`checkDocSets_ignores_commitments`); so beside `judgments@0` it is G3's,
  and in its own mode `judgments@0` is a document layer (`CommitmentsBesideJudgments`, CM-2's).

  Draft 1's `pairTheorems` (a list of `Lean.Name`) is deleted: a listed name does not show that the theorem is
  about the route.
- **G1 and G4** are not restated. Over readings they are `superpose_all_extra` at `Q := Packs.X qs`, discharged by
  `transfers_X`, through `Readings/SupPacks.lean`'s join, so `Choice_D` and PK-1's `X` are one premise list
  (`slotUnder D A ++ Packs.X qs`; PLANS-INDEX D14 is now the rule). Off readings, G1 is `acceptanceX` at
  `X := Packs.X qs`. Draft 1's `Composed` and `composed_acceptance` are deleted.
- **G1b** (`acceptanceXV`, `entailsXV_constraint`, `countermodelXV`) is owned by PK-1's owner, in a new module
  beside `PacksLegacy.lean`. `Packs.lean` is not touched by this plan. It takes assembly's freshness (no pack name is
  declared in `fullEnv U`), and its base and expansion are admissible over the extended vocabulary (`envX U qs`,
  `fullEnvX U qs`) in place of the old one, so a true fresh pack predicate has a model (specification 1.6).
- **G3** is restated as success-only transparency on `checkDocSets` (PC-1, specification 1.7), over comparison
  pairs: the twin's stated identities are exchanged for the twin environment's (2a), and neither side states a

## 4. Exceptions and priority in one composed document

### 4.1 Two typed priority graphs (PC-9)

- **Defeasible rank, over ranks.** Soft-norms owns `outranks`, checked by its rank check (`RanksValid`,

`VE.Closure` stays the one closure. The kinds keep their meanings: strict precedence decides where both rules
apply, and rank acts only through exceptions. The weighing plan's own warning stays true: where the higher rule's
exception applies, the lower may decide.

Draft 1's `pairs` erased the vertex type. Rule `a` over rule `b` beside rank `b` outranking rank `a` then made a

### 4.2 One "no exception" (PC-9 statements, EXP-D3, defeasible owns the build)

The conditions come from soft's own exceptions and from **provider-exported condition metadata**. PK-1 adds the

The hazard this prevents (research 5.2): `dfltLabelled` adds `¬outweighs(a, L, H)` for every ranking triple. A

### 4.3 Split rules share one decision (PC-6)

When acts splits a soft rule into part rules, every part keeps the parent's mode, rank, exception and switch, and
reads the parent's decision atoms. A decider makes one call for "adjust, correct, retrain, or shut down", as the
source makes one rule. A split must never quietly turn one call into four.

This needs an explicit representation change. Today `exceptedName` and `offName` are built from the node's own name
(`SoftNorms/Tree.lean:266-267`), so renamed parts would get distinct decisions. PC-6 therefore adds:
- **A decision key.** The field `SoftNode.splitFrom`, read by `decisionRule`, names the rule whose exception and
  switches a rule reads. On an unsplit rule it is today's key, byte for byte (`exceptedName_unsplit`,
  `offName_unsplit`). Soft-norms owns the field and the two names, and its owner reviews them.
- **The argument mapping.** Parts keep their source predicate's argument sorts (`splitEnv`), so a part's decision
  atoms take the source's arguments in the same positions (`split_sorts`).
- **Preservation, proved before any refusal is lifted.** Parts share the exception and every switch
  (`split_shares_decisions`), and the split document's decisions are the source's, one per key (`split_decisions`).
  These statements take the checked elaboration, `elaborateMap A = .ok E`, not the `SplitMap` alone: the map
  holds names and indices, and `splitReg` reads the act atoms (`Elaborate.lean:93`).
- **The decision table and its invariant.** `keyedDecisions` keys every entry by `decisionRule` and keeps equal
  entries once, and `decisions` is its values. The invariant is restated as equality of decision keys with
  consistent sorts (`decNodup`, on the deduplicated table) and exception metadata (the new `SoftValid` field
  `decMeta`). This replaces `excepted_inj` (`Defaults/Meaning.lean:105`) by `excepted_key`, and restates
  `decisionNames_split` (`:100`) and `decisionNames_eq` (`SoftNorms/Semantics.lean:834`). Draft 2's claim that
  only two theorem statements change is withdrawn. Specification 1.10 lists every revised statement and every
  caller by file and line.

`outweighs` decisions are per act, and a split act's parts are distinct acts. So PC-6 admits a split only under
strict outranking, and refuses one under holistic outranking until soft-norms' owner decides how an `outweighs`
decision reads across parts (specification 1.10).

## 5. Judged terms

Decision for this plan:

- Test, by EXP-J1, whether a finer Lean-computed field, **decided given calls**, is honest and useful on the

A call is a decider's finding on a judged atom. It is recorded on WG-6's records, as judgment-terms D8 and D14

"Decided given calls" must state three things:
- the assignments of the unit's judged atoms are exhaustive;
- there is at least one point, so `points = []` never passes vacuously;
- the unit has no other openness.

### 15.2 How a unit's composition is written in the designed notation

A writer who writes this plan's part of a unit, and stubs other families' spans as `STUB[<family>]`, uses these rules
(the full ruled grid: every batch of section 8 landed, the staged ones included):
1. **One document, one sorted profile list**: every profile a unit's construct needs, admitted families' and stubbed
   families' alike, because the list decides the route.
2. **The stack** is the list's rewriters in rank order: `ve.discourse@1` (10), `acts@0` (11), `scope@0` (12),
   `right-clauses@0` (20), `readings@1` (30) (2.1, `stackOf`).
3. **The stack rule.** No stack, or one rewriter: no rule applies. Two: the pair must be listed. Three or more: the
   stack must be listed, which the listing rule does once every pair is (1.5 of the specification). Listed pairs:
   `scope` + `readings` (main), `acts` + `scope` (PC-6b), `discourse` + `scope` and `discourse` + `acts` (PC-7b),
   `discourse` + `readings` (PC-7c), `acts` + `readings` (PC-6c). Any pair with `right-clauses@0` is unlisted, so
   refused with E1, naming the first unlisted pair in stack order.
4. **Layers.** `judgments@0` (needs `documents@1`) composes with every admitted list (G3); its reader reads every
   content kind, attitude nodes' contents included (PC-1b). Any other layer only where its own theorem covers the list
   (the layer rule, PC-4).
5. **Packs** (`weighing@0`, `attitudes@0`, `scales@0`, `events@0`) put premises in `X` (G1, G1b, G4); an attitude node
   is a guard conjunct (AT-3a).
6. **Records.** `commitments@0` is a document record: its block is front matter that no decoder of the document mode
   reads; its own checks are its mode's (PC-4's record rule).
7. **Outside route heads** (`alternatives@0`, `risk@0`, `speech-acts@0`, `reports@0`) beside the chain stay refused until
   a bridge (EXP-O1).
8. **Candidates.** A reading candidate holds one content (composition's `Content`). A candidate that needs more, or a
   profile the list lacks, stays pending (`content: null`); its rows are `unknown`, never dropped (rule "one reading
   per sentence").
9. **Stubs fill slots.** An attitude: one guard conjunct, with its holder, its slot (the rule's quantified variable)
   and its content. A commitment: the front-matter block entry of a unit or a candidate (bearer, strength); its bearer
   is the act's first argument (commitments D5). A scope effect: a governor of the scope block (unit, reach, effect)
   and, for a governor whose words have readings, the reading set on its own unit. A quantity or a collective
   antecedent: the argument position it fills. An event-relative duration: a MIXED part with status UNFORMALISED
   (`duration`). (pc-fid-rev2) **A modal or scenario condition** that limits which situations a rule binds ("might X,
   in which case …", "if X were …"): the last conjunct of the guard of every candidate whose rule it limits, written
   "…, if both <the rule's own condition> and ⟨STUB[modality-counterfactual]: "<the condition's words>" (scenario σ,
   at that situation)⟩"; the stub receives the rule's quantified variable as the scenario's situation variable, and a
   condition that is closed or has another free variable is refused `ScenarioUnbound` (modality's); the possibility
   itself is the scenario's admission, not a conjunct (PC-12, staged on MD-4a; specification 3.11). The same
   condition in a unit of its own ("Suppose that …") is modality's governor in the scope block, whose `reguard` gives
   the same guard. **A filler act phrases' grammar does not derive** (a run of filler words beside a fixed phrase in
   one argument, "significant “moonshot R&D for security” projects"; act-phrases 1.4, 5.2): the act's argument
   position, `STUB[act-phrases]`; its grammar is the follow-up row ap-mixed-filler's, and the candidates holding the act
   stay pending. **A limiting purpose's words**: the judged words of the guard's judgment conjunct (rule 12),
   `STUB[purpose-explanation]`; its link (the rationale reading) is purpose-explanation's purposes block.
10. **Couplings (pc-fid-rev2, R1).** A coupling is main's: every candidate of every set it names carries a label on
   its axis and the sets share a value, otherwise main refuses the document at decode, before any route, with
   `CouplingLabelMissing: <coupling id>, <set id>` (the first set, in the coupling's order, with an unlabelled
   candidate; specification row 20). This plan relaxes none of it. A set whose candidates differ on more than one axis
   (the RSP use case's one set {F, Ds_strict, Ds_default}: the addressee, and for Ds the force) is written either
   (a) with **one combined axis** whose values are the set's candidates (`rs2` = `F`, `Ds_strict`, `Ds_default`) and
   one coupling on it, or (b) with **one coupling per axis**, every candidate of every set that coupling names
   carrying its axis; a candidate the axis does not apply to carries its own id as its value (`force=F`), the same in
   every set of the coupling. A set that shares only some axes (ursp.t4_evidentiary's: the addressee, not the force)
   is named only by those couplings and carries only their labels; in (a), the sets sharing the combined axis also
   carry that shared axis. Both forms give the same choices (F2.10: 5 of 27).
11. **An act phrase with more than one derivation inside a candidate (pc-fid-rev2, R2).** Read the phrase with act
   phrases' grammar: a split object or a split marker's list followed by a modifier has two derivations, the modifier
   over the last part or over every part (act-phrases 5.2, lines 697 and 711). Write one candidate per derivation, the

   GAP owned by act phrases: its candidates are pending (PC-6c; specification 3.6; F6.17).
12. **A purpose clause after a rule (pc-fid-rev2, R4(a)).** "<rule>, so that <Y>", "<rule>, to <Y>", "<rule> for <Y>"
   with both readings (purpose-explanation D6(a)) is one reading set on the part that holds the rule and the clause:

   33-36, 116), read by PC-1's `judgedIn`; and `rationale`, the rule as written, with purpose-explanation's link (no
   premise). Or narrow it to one with a cited source unit. Never a link part alone. With an outer set the candidates
   are the pairs, as in rule 11; under PC-6's split the conjunct is in every part rule's guard (PC-1, PC-2b;
