### 2. import-linter replaces the custom resolver where it can (`9a0b0f4a`)

The plan's claim holds for `tools/check_python_layers.py`: it no longer resolves imports or recomputes edges.
`lint-imports` on the generated `.importlinter` finds every outward import, direct or through other modules, and
(with `unmatched_ignore_imports_alerting = error`, now in the contract) fails on a ledger edge that no longer
exists. The script keeps only what import-linter does not check, each with a fixture test:

- a module no row places fails ("unmapped Python module"): there is no default layer;
- a directory of modules without `__init__.py` fails (import-linter would not see its modules);
- a ledger edge that is no longer outward under the table is stale;
- the `__init__` of a package split across layers (`ve.backends`) is in no import-linter layer (import-linter refuses
  nested layers: "Modules have shared descendants"), so the contract lists the package's other modules one by one
  and the script checks that `__init__`'s imports;
- a module below the facade's highest layer (4) may not import the `ve` facade: its names now resolve lazily, so
  import-linter sees an import of `ve`, not the module behind the name.

Kept, with reason: `layer_policy.python_imports`, the per-file resolver. The pre-commit hook
(`tools/hooks/precommit.py`, left alone here) checks each staged file without the rest of the
tree, which import-linter cannot do; the hook's tests pass unchanged except `ve.ast`'s new layer number
(`tests/test_precommit_hook.py`). `python_exports` stays too: `tools/select_tests.py` (not to be edited) imports it.
The one layer table stays in `tools/layer_policy.py`; the one reader of the facade's table is
`layer_policy.lazy_exports` (used by the layer check, the hook, `tools/change_units.py` and
`tools/semantic_inventory.py`).

### 3. Package rules, no default layer (`9a0b0f4a`)

A package's row places every module under it (longest row wins), so a new module in `ve/backends/`, `ve/document/`,
`ve/assist/`, `ve/readings_verdicts/` or `ve/surface/` needs no row; a longer row overrides it. App areas
(`ve_experiments` and the other `APP_AREAS`) are layer 5 by rule in `python_layer`. A new top-level module still needs
its row: no rule places `ve/calc.py`-like route modules without being wrong for containers that relay too. Tests:
`test_new_module_in_a_placed_package_needs_no_row`, `test_seeded_module_with_no_layer_fails_the_check`.

### 4. `ve/__init__.py` resolves its names lazily (`31af3a87`, `a844ce2b`)

`_EXPORTS` is the one table of the 83 public names; `__getattr__` imports a name's module on first use, and any
submodule as an attribute; `__all__` keeps `from ve import *`. `check` and `evaluate` name both a function and its
module, so a property on the package's class keeps them the functions after `import ve.check` (as the eager file
did). Two behaviours depended on `import ve` loading everything and are kept:

- `ve/surface/__init__.py` loads `ve.ast` first, the order `import ve` imposed (entering at `ve.surface.registry`
  otherwise fails on the `ast <-> surface.nary` cycle). Probe: every one of the 151 `ve` modules and 83 names
  imports alone in a fresh interpreter.
- `ve.argument._checker_build` fingerprints every surface record; `ve.english` registers one at import. It now
  imports `ve.english`, so the build value does not depend on what was imported first
  (`test_checker_build_does_not_depend_on_what_was_imported`). The record set equals the base's
  (`_checker_build` spied at base and head: 33 identical tags).
