Verifiable English, from first principles

Write what you mean in ordinary English. Make the assumptions visible. Let a small checker verify what follows.

Verifiable English (VE) is a research project building an English language for precise commitments: policies, contracts, procedures, scientific claims and more. Its goal is that an English speaker can read and write it without training, while every admitted sentence has one formal reading and every accepted deduction carries checkable evidence.

The focus now is expansion. Since 25 September, new work has focused on making VE express more while preserving its properties. New experiments seeking an oversight benefit are parked. Better authoring and checks of translation fidelity remain part of building the language.

Start with sections 1–4; no logic background is needed. Later sections explain the machinery, evidence, current work and demo. This is a dated snapshot: merged, branch prototype and planned mean different things. Zero-training usability is the goal, not a result already established with people.

SECTION 1

Why VE exists

Suppose someone gives you a long argument that a software release is safe. Reviewing it mixes several jobs: checking the reasoning, checking the facts it starts from, deciding what “safe” means, and noticing requirements it left out. A fluent argument can make these jobs hard to separate.

VE separates the deduction from the rest. Consider:

Every reviewed service is safe. The API is reviewed. Therefore the API is safe.

The last sentence follows from the first two. A checker can establish that without knowing anything about software. It cannot establish that a review really happened, that reviews guarantee safety, or that this is the right definition of safety. Those are still questions about the premises and their intended meaning.

Checked deduction

Does the conclusion follow from these exact premises, using these exact definitions?

Visible residual

Which assumptions, open terms, interpretation choices and external sources does the conclusion still depend on?

A residual is the work left after checking. It may be difficult or large. The aim is to name and preserve it so that a proof does not make an uncertain foundation look certain.

This began as work on scalable oversight: how a person or weaker AI can supervise work they cannot reproduce in full. That motivation remains. The immediate task is to expand the language and its writing tools, with guarantees that survive the expansion.

Three answers, each honest. “Follows” comes with a checked proof. “Does not follow” comes with a checked counterexample. “Unknown” means the system could not establish either within its limits. Unknown never counts as success.
SECTION 2

English first: what you read is what you should be able to write

The lead principle is zero-training English, for reading and writing. An ordinary workflow should need no syntax manual, variable letters, brackets, operators or special name markers. The assistant should resolve ambiguity by asking questions in English. It should not ask the writer to learn a second language.

The natural-view branch shows concrete progress. These before-and-after pairs come from its checked examples; the longer “before” forms are the older technical display.

Before · older fluent view

For every service S that is deployed, S is reviewed.

After · natural view

Every deployed service is reviewed.

Before · older fluent view

For every service S that is deployed, there is a person P such that P owns S.

After · natural view

Every deployed service has an owner.

The second sentence allows different services to have different owners. It does not say that one person owns them all. The shortening is currently licensed by a particular declared ownership wording and its argument order; it is not a general guess about what “has” means.

Before · the web example

Every reviewed service is safe.
Api is reviewed.
Api is safe.

After · one paragraph, with a checked conclusion

Every reviewed service is safe. The API is reviewed. Therefore the API is safe.

“The API” is a declared display name for the same object. “Therefore” marks a conclusion: the branch’s argument parser must find a replayable proof from the preceding premises. It cannot quietly turn an unproved conclusion into an assumption. Paragraphs, three-item lists, locally bound relative clauses and a limited “it” reference are also implemented on that branch.

How the natural view earns admission

The renderer proposes a sentence, then parses the exact displayed text back. It must recover the same structured claim and find exactly one grammar derivation. The whole displayed paragraph is checked too. If a short form fails, the renderer uses an audited explicit English form and gives a reason.

A prototype with known gaps. The recorded corpus has 599 natural forms out of 1,219 samples (49.1%); the real-use-case subset has 73 out of 96 (76.0%). The other 620 use explicit forms, often with technical notation. Those are zero-training coverage gaps. Zero accepted wrong AST readings in this corpus is a round-trip result, not proof that people interpret every sentence correctly.

As of this snapshot, the natural view is on expand/natural-view and incorporated into the separate web-app branch, not merged into integration. One reviewer cleared it; the latest other review requires fixes for colliding display names, a command-line path that loses conclusion roles, and missed pronoun referents. The examples above demonstrate the intended branch behavior, not completion of those fixes.

When the tool cannot understand a sentence

The zero-training plan calls for English paraphrases, concrete example situations and editable rewrites. If nothing faithfully expresses the intended meaning, that part remains visibly unresolved. Technical fallback may help a developer inspect a problem, but it does not count as successful ordinary-English authoring.

The plan was revised after review to specify recovery from unsupported input, a deterministic catalogue of ambiguity patterns, alternatives when a model is unavailable, and safer reference resolution. Those are planned mechanisms, not completed behavior. For example, “The API is deployed. Some service is reviewed. It is safe” introduces another possible referent even though only the API has a name. One grammar derivation alone does not settle all the interpretations an English reader might consider.

SECTION 3

Words and whole documents

The long-term target is a checked spine: the definitions, claims, obligations, quantities and evidence a document commits to. Explanations, examples and figurative prose stay visible and labelled. A document need not turn every sentence into a theorem.

The document plan requires every source span to belong to a recorded unit. Unsupported material gets a reason; it is never silently omitted. Accounting for 100% of the source does not mean formalising or proving 100% of it.

Three descriptions replace “judgement call”

QuestionWhat is recordedExample
What kind of content is this?An assertion, definition, obligation, attribution, hedge, question, instruction, example or exposition. Kinds can nest.“Alice believes the service is probably safe” is an attribution containing a hedge.
How settled is its meaning?Fully specified; dependent on a declared context; constrained but open; or not yet formalised, with a reason.“Reasonable precautions” is open-textured.
What supports it?An assumption, proof, observation, calculation, statistical assessment, testimony, adapter output or no support.“The API was reviewed” might be supported by an audit record, not a deduction.

This distinction prevents “someone said it” from becoming “it is true”. To use an attributed claim as a premise, the document needs an explicit bridge assumption, such as accepting that source’s statement. A later proof must retain that dependency.

Open terms are legitimate vocabulary

“Reasonable”, “harmful” and “appropriate” often need judgement when applied to a new case. VE’s design keeps such words as named open predicates: properties whose surrounding logic is exact, but whose application needs a recorded decision.

Example: “reasonable precautions”

The document records who decides, any necessary conditions, sufficient conditions where known, factors to consider, pinned examples or precedents, and the jurisdiction and version. A rule can then say that anyone handling a hazard must take reasonable precautions. Applying the term awaits the named decision-maker; the ruling enters as a labelled premise.

Inventing a numerical threshold would not remove the judgement; it would change the rule. Naming a decision-maker does not prove that their decision is correct. The benefit is an explicit, reviewable dependency. The open-term schema is part of the documents workstream, which is still in review.

Synonyms without shifting meaning

Writers should be able to vary words. The adopted design allows a glossary declaration such as:

In this document, staff, employees and personnel mean the same thing.

These become aliases for one concept, while the display retains the writer’s word choice. Meaning identity is separate from spelling. The definitions work must prove that an alias preserves the old meaning and validate its argument types and direction; cycles and collisions are rejected. This is a planned use of the definitions machinery, not a completed end-to-end synonym dialogue.

In authoring mode, the proposed interaction is “Does personnel mean staff here, or a different group?” The author confirms. In translation mode, an explicit source definition is recorded with its citation. Synonymy inferred only from context remains an interpretation: keep both same-group and different-group readings where relevant, and disclose which conclusions depend on the choice.

A pinned Open English WordNet lexicon supplies word classes, morphology and candidate senses to proposal tools. It is advisory. A dictionary entry cannot establish what this author meant or make two groups identical.

SECTION 4

Two modes: authoring and translation

When you write a new document, you can say what you meant. When you translate someone else’s document, you cannot silently make that decision for them. VE uses the same reading set in both cases, with different rules for closing it.

Ambiguous source · proposed clarification example

Every engineer checks a server.

Reading A: possibly different servers

Each engineer checks at least one server. Alice can check Atlas while Bob checks Beacon; they need not share a server.

Reading B: a shared server

There is at least one server that every engineer checks. Alice and Bob might both check Atlas.

The first situation separates the readings: A holds and B fails. B implies A, so a situation with a shared server does not distinguish them in the reverse direction. The planned IDE must validate example situations and proposed rewrites through the checker and parser. These teaching paraphrases describe the plan; they are not a claim that today’s interface offers this complete interaction.

Authoring

The author selects and confirms the intended reading. Rejected alternatives stay in the history. Approval is bound to the meaning and reviewed source; edits invalidate the approval and affected dependent approvals.

Translation

The source keeps its admitted alternatives. A translator, court or adopter may record an attributed narrowing, with reasons and citations. That creates a separate interpretation record; it does not erase the source’s alternatives.

Mode belongs to each unit, not necessarily the whole document. You might author a policy’s new clause while translating an older quoted clause. A reading set means “readings considered so far”: versioned, open to challenge and extension, never a promise to have enumerated every possible English interpretation.

What a conclusion can say

ReportEvidence required
All readingsA checked proof covering every admitted complete choice.
Some readingsA proof for a named choice and a checked countermodel for another.
No readingsChecked countermodels showing non-entailment under every choice. This means the conclusion is not established by any choice, not that it is false in every possible world.
UnknownThe evidence or supported route is insufficient, or a budget is exhausted.

A reading choice stays the same throughout an argument. Citing a result imports its interpretation choices and assumptions; incompatible choices cannot be combined. Expanding a set makes affected old results stale. Translator probabilities are removable annotations outside checking; deleting them must not change a verdict.

How the plan avoids unnecessary enumeration

For assertion readings with identical background premises, the checker can prove “all” from a disjunction of each unit’s alternatives. A single shared countermodel can establish “none” if it satisfies every reading and refutes the conclusion. These shortcuts do not apply when a reading changes definitions, obligations or other background conditions. The plan then checks complete choices separately, up to 64; beyond that it reports unknown. The current documents branch remains incomplete, including support for non-assertion reading routes.

Corpus priors: an advisor on the backlog

A converged design proposes transparent corpus counts beside reading alternatives. It would start with whether a prepositional phrase attaches to a noun or a verb, using a pinned annotated English corpus and a published matching method. A note would show the actual counts, document count and examples, with abstention when support is sparse or unsuitable.

This is a backlog research adjunct, triggered after reading sets by at least three consequential attachment ambiguities in a translated pilot. It needs calibration before IDE use. The annotation must never remove, preselect or reorder readings, create a synonym alias, or affect certification. Corpus frequency is not a probability that this author meant a particular reading.

SECTION 5

How checking works

  1. 1. English and vocabularyState the claims and declare what the words refer to.
  2. 2. Exact meaningParse the text into structured claims with versioned identities.
  3. 3. Untrusted searchLook for a proof or a counterexample within a budget.
  4. 4. Independent checkingReplay the evidence and report the remaining dependencies.

A small logic primer

A sort is a kind of thing, such as a person or service. A constant names a particular thing, such as the API. A predicate states a property or relation: a service is reviewed; a person owns a service. Words such as “every”, “some”, “and”, “not” and “if” combine these into claims.

A model is a possible situation: which objects exist, and which properties and relations hold. Premises entail a conclusion if the conclusion holds in every allowed model where the premises hold. Evaluating one model only tells you about that situation.

Three tiny arguments

These are worked illustrations, not a checker running inside this page. Open each to inspect the reason.

Every cat is an animal. Tom is an animal. Must Tom be a cat?

No: it does not follow. Tom could be an animal that is not a cat. That possible situation makes both premises true and the conclusion false. It is a countermodel. It does not tell us whether the real Tom is a cat.

Every cat is an animal. Tom is a cat. Must Tom be an animal?

Yes: it follows. Apply the first sentence to Tom, then use the second. A proof certificate records the steps so the checker can replay them without rediscovering the proof.

Every service is reviewed. Must some service be reviewed?

No: there might be no services. VE allows empty sorts. “Every service is reviewed” is true when there are none; “some service is reviewed” is false. If you need existence, state it. A declared named service would also supply an inhabitant.

Finding a proof can be hard. A proof certificate records which rule applies at each step, making replay much simpler than search. VE’s tableau checker reasons by assuming the premises and a false conclusion, then checking that every resulting branch reaches a contradiction. Other supported profiles add specialised certificate rules.

Soundness means that an accepted certificate establishes the deduction. It does not promise that search finds every valid proof within its budget. General first-order entailment is undecidable; finite countermodel search can also miss counterexamples that require a larger or infinite world. Exhaustion therefore stays unknown.

Identities keep meaning fixed

The environment_id identifies the declared vocabulary and semantic context. A meaning_id identifies the canonical structure of a claim under that environment. Changing a definition or profile cannot silently reuse the old semantic identity. Presentation-only changes, such as a validated display name, can preserve it.

Identical meanings can have different approved spellings, and different structures can sometimes be logically equivalent. VE’s comparison tool tries to prove equivalence in both directions or find a distinguishing countermodel. If it cannot, it says unknown. Hashes bind the chosen formal objects; they cannot establish that those objects capture the writer’s intent.

Claims compose, and assumptions travel with them

A claim graph joins deductions together. Each edge has evidence; each unproved starting claim remains an assumption. A result is reported with its dependencies. The new setup contracts also preserve labels for source attribution, background premises and interpretation choices.

Expand the language without silently changing its logic

Elaborate by default; extend only through declared, verified profiles. This is the converged rule adopted after the planning debate.

Elaboration means translating a convenient new construction into an existing checked language. It needs a Lean proof that the translation preserves independently specified meaning, including the correspondence between possible models. A profile is a named, versioned package of supported semantics and checking rules.

A new profile needs a concrete document whose intended inference cannot be handled faithfully or within the existing budget. Before admission, it needs explicit semantics, sound certificate checking, valid countermodels, safe composition with other profiles, and a proof that old claims keep their meanings and consequences. Existing identities, bytes, certificates and theorem statements stay frozen. Tests across Python, Rust and Lean supplement those proofs.

A separate checker’s result can enter a deduction only through a verified bridge preserving its assumptions and kind. Likewise, a default-based conclusion must remain a conditional result about a fixed, recorded rule set; adding unrelated material cannot silently retract a certified edge. Truth in the world, interpretation and open-term decisions remain outside deductive certification.

SECTION 6

What is proved, tested and judged

Lean is a programming language and proof assistant whose kernel checks mathematical proofs. VE has reference semantics and checker soundness proofs in Lean. The practical Python implementation and Rust evaluation/search paths are tested against that reference. They are not thereby proved equivalent to it.

Proved in the reference

Deductive certificate soundness; finite evaluation and countermodel results under their stated validity conditions; the base strict parser/printer round trip; graph composition; reachability and closure induction; order checking; and the new layer, background and labelled-admission contracts.

Tested in implementations

Python/Rust/Lean agreement on supported cases, rejection of forged certificates, English parsing and rendering, identity and wire handling, and the natural-view corpus. Tested agreement is evidence over the tested inputs.

Still reviewed or measured

Premise truth, fidelity to source or intent, applications of open terms, completeness of requirements, the suitability of a model, and whether people can read and write the language without training.

What the tests do—and do not—say

The recorded integration run after the setup merge had 1,701 passing tests. The English-surface baseline separately reports 85,000 structured-claim round trips and 12,750 all-derivations texts. Those are different cohorts, not 85,000 independent proofs of English unambiguity.

The merged admission policy checks all grammar derivations for each accepted English input. Ambiguity or an exhausted checking budget rejects admission. That is stronger than relying on a test corpus, but the parser implementation and its correspondence to ordinary English still need scrutiny. The full Lean proof of the writable English surface is deferred until the grammar settles. The order parser’s round-trip theorem is also not complete.

Use precise assurance language. “The Lean reference checker is proved sound” is accurate within its stated semantics. “The whole VE system is formally verified” is not. Wire-format correspondence, hashing, Python refinement, compiler/runtime behavior and human interpretation remain outside the proved boundary. Some executable model-validity and admission results are proved; that does not verify the entire input and output path.

Inconsistent premises can prove anything. The expansion contracts therefore require separate reports for a satisfying model, proved inconsistency, or unknown consistency, and mark deductions from inconsistent premises as vacuous. A proof badge alone is not enough. The demo’s current limitation here is described next to its instructions.

Examples of the limits the plan makes explicit

Rules with exceptions. A policy might permit access unless a named prohibition applies. VE plans static, ordered exception structures and checks the completed outcomes. If a policy requires an action but denies permission for it by default, that is a conflict even if no explicit prohibition was selected. A conflict-free verdict needs a proof; merely failing to find a conflict is not enough outside a separately proved bounded fragment.

Numbers with meaning. The planned quantity layer represents 3.75% by a scaled integer plus a unit tag. It must not confuse that with a money amount encoded by the same integer. Dates and deadline endpoints need stated conventions. General real arithmetic and unit conversions are not delivered by this representation.

Counting within a bound. Planned counting sugar expands “at least” up to eight witnesses, and “exactly” or “at most” up to seven. “16 of the 18 policymakers” remains outside those bounds. Turning a number into an opaque predicate would not count as checking its arithmetic meaning.

Authoring before offering. The planned gate seals 20 sentences per construct before tuning, requires at least 80% faithful authoring and zero certified-but-unfaithful load-bearing nodes, and separately checks 20 rendered witnesses. A failing construct stays available only through technical forms. Model-based audits are proxy evidence; human readability remains unmeasured.

The revised zero-training plan ties these streams together: one readable and writable surface, an English clarification loop, vocabulary dialogue, persistent approval history and measured coverage on whole documents. It now specifies recovery and deterministic alternatives after both reviewers requested changes; recheck and implementation remain ahead. New presentation versions must preserve old rendering and semantic identities. Its proposed coverage and completion percentages are pilot targets, not demonstrated usability rates.

SECTION 8

Try the web writing desk

A separate branch, expand/webapp, provides an authenticated web app with four curated examples, a writing desk, natural English, an advanced strict inspector and small example worlds. The recorded VM deployment uses HTTPS, with live assistance enabled after a restart fix. It is a private demo, not a public service linked from this page.

  1. Start in Learn. Choose a curated example. Read its natural view and notice any “explicit form” badges. Those badges identify readability gaps.
  2. Separate assumptions from the conclusion. Replay a deduction, or inspect a checked world where the assumptions hold and the conclusion fails. Try the reviewed-service example from section 2.
  3. Edit in the writing desk. Check the consequence with the on-screen control or Ctrl/Command+Enter. Strict source and vocabulary/world data remain available under advanced disclosures.
  4. Use assistance only when wanted. If configured, a click requests candidate readings for one sentence. Nothing calls a model while you type. The gallery and checker do not call models.

The default assistance allowance is three calls per rolling minute and 30 per UTC day, shared across sessions. Suggestions require explicit review and acceptance. The initial vocabulary comes from the chosen example; this is not yet unrestricted English authoring.

What “Certified” means here. The experimental Python checker replayed the exact deduction. The app does not run Lean and does not perform a separate premise-consistency audit. A finite-world evaluation is not an entailment proof or evidence about the real world. Unknown is not success.

Accepting a candidate is a local drafting action, not an approval in a persistent audited authoring ledger. Drafts live in the current tab; reloading loses them, and switching examples replaces them. The app’s JSON draft export preserves a draft, but its explanatory provenance is not a signed authorship certificate. The zero-training plan must supply the persistent, replayable workflow.

Setup instructions: git show expand/webapp:webapp/README.md. The README’s original fixed-CLI setup is superseded by the app-only Controls fix at 37494ac; the recorded batch-two natural-view merge is 34f8fcb. No live assistance was invoked while updating this tutorial.

Keep the useful asymmetry: evidence can be easier to check than to find

Suppose an account cannot reach a secret through a network of access grants. A certificate can list a set containing the account but excluding the secret, and show that every grant from inside the set stays inside it. Any path stays inside too. This is a separating certificate; the preserved property is an invariant.

Account A can reach its team; the team can reach a report. The set containing A, the team and the report is closed under those grants and excludes the secret. Add a grant from the report to the secret, and the certificate fails.

VE’s Lean-proved closure-induction rule supports this reasoning. It still assumes the declared grant graph is complete. Ordinary graph-search software is also a strong baseline; a certificate benefit is not automatically a benefit of English or of VE.

Mandatory proof and its boundary

Under a mandatory-proof rule, a claim is accepted only if it has a checked derivation from reviewed foundations. An arguer cannot smuggle in a false intermediate claim merely because it makes later deductions work. If no affordable proof is available, the claim stays unresolved. False foundations, a mistranslation or omitted requirements remain possible failures.

For uncertain empirical claims, the proposed evidence layer would attach source records, reproducible calculations and defensible uncertainty bounds. It remains later work. Checking a calculation does not validate its data or justify an independence assumption.

Protocol directions remain research

A proof-carrying action would bind a checked policy result to the exact tool call and relevant state before execution. Authentication would prevent an agent from forging the checker’s verdict; it would not establish premise truth. These are research directions, not features of the writing desk.

The old “next studies” queue is superseded. The pushback study as specified was stopped after formal-item gates showed no flips at either tested pressure level. New benefit experiments are parked. Existing offline work was allowed to finish a pass, and the long-policy leakage audit later aborted without a result. This page makes no new experiment efficacy claim.

SECTION 10

How the project runs now

The orchestrator is the directly responsible individual (DRI): it decides the next step, assigns work, integrates it and reports briefly. The human lead sets direction and acts as an occasional adviser. Decisions and state live in files so work can resume after interruptions.

Implementation

GPT-6 Sol handles most Python, Rust, interface and test work, including simpler Lean tasks. Claude Opus 5.5 handles the hardest Lean proofs. Each worker uses its own Git worktree.

Planning and review

GPT-6 Astra and Claude Fable 5.1 review and plan at extra-high reasoning effort. Plans get both reviews; implementation gets review across model families and a narrow recheck after fixes.

  1. Plan against explicit contracts. Agree on semantics, proof obligations, ownership and acceptance evidence before building.
  2. Fix concrete defects. A reproducible bug from either reviewer gets a fix and recheck.
  3. Resolve real disagreements by convergence. Reviewers exchange their full written rounds through shared files, without an intermediary summarising their positions. They repeat until both record convergence; if they cannot, the playbook says to lean toward Fable.
  4. Integrate and verify. Run the full test suite, Lean build and theorem audit after merges, alongside the required conformance and feature checks. Tag a green integration state.
  5. Continue from completion events. Every launched worker needs a wake-up mechanism. The orchestrator reads the result and starts the next authorised step rather than leaving completed work unattended.

Usage and machine limits are part of the workflow

Usage guards must keep every session and weekly pool below 90%. Heavy Claude workers start only below 40% of the five-hour allowance, leaving room for the orchestrator. Reset times guide scheduling; capacity is not permission to start new benefit experiments. On the current eight-CPU VM, the playbook recommends roughly five or six concurrent workers and reducing concurrency when load threatens timed jobs.

The VM should be safe to resize at any time. Workers commit often; a checkpoint process snapshots uncommitted work about every 20 minutes, writes an in-flight relaunch list and records safe/unsafe status. Non-resumable work must be registered. The aim is resumable long jobs, not assuming that a snapshot can rescue every in-flight computation.

Local commits preserve progress. The current playbook says not to push. Historical experiments retain their preregistrations, amendments and corrections; a changed analysis is recorded rather than silently rewritten.

SECTION 11

Your first contribution

Begin with a short text you care about. Identify its commitments, assumptions, ambiguous readings and unsupported parts. A useful contribution is often a precise gap with a concrete example, rather than a larger feature or a new benchmark.

Try to preserve a paragraph

On the natural-view branch, compare source, displayed prose and parsed meaning. Change a name, negation, pronoun or conclusion marker. Report any lost role or changed scope, including cases a test corpus misses.

Account for every sentence

Follow the document format on its branch. Mark each span’s kind, meaning status and support. Keep unclear and unformalised material visible. Report residual counts and fidelity disagreements separately from coverage.

Check a feature boundary

Compare the new feature’s advertised profile with its actual parser, model validator and evidence route. Unsupported combinations should reject clearly; exhausted searches should never become positive verdicts.

Make a witness readable

Turn a checked countermodel into a small situation using the document’s own names and units. Verify that it still describes the same model and that a reader can locate the failed conclusion.

A local starting workflow

These commands use deterministic tools, not models. Run them from the integration checkout. They build the reference, audit the proofs and reproduce the empty-service countermodel. A full test run is appropriate for an implementation change; this tutorial revision re-ran the theorem audit and page checks, not the full project suite.

uv sync
export PATH="$HOME/.elan/bin:$PATH"
(cd lean && lake build)
python3 lean/audit.py
uv run python -m ve countermodel --env examples/environment.json \
    --premises examples/premise.ve --conclusion examples/conclusion.ve

# For implementation changes:
uv run python -m pytest

Coordinate shared-file changes with the owner in the expansion plan. Natural-view and web-app commands belong to their branches; their presence in this tutorial does not mean their modules are available in integration.

Questions that remain open
  • Can ordinary English speakers reliably understand and author unfamiliar commitments without training?
  • Can a reviewer notice a faithful-looking statement that quietly weakens the source?
  • How much useful document coverage can elaboration provide before search becomes impractical?
  • Do explicit residuals make review easier, or merely move the hard work?
  • When do certificates add value over strong conventional software and direct review?
SECTION 12

Glossary

Abstract syntax tree (AST)
The structured representation of a claim: objects, predicates, scope and logical connections. A round trip checks that displayed text parses back to the same structure.
Admissible model
A possible situation satisfying the vocabulary’s types and the profile’s declared conditions. A proposed counterexample must pass these validity checks.
Alias / synonym
A declared alternative wording for one concept. A valid alias preserves meaning and argument roles; apparent similarity alone does not establish it.
Authoring / translation
Authoring lets the responsible author confirm one reading. Translation preserves the source’s admitted alternatives; attributed narrowings remain separate.
Background premises
Conditions generated from declarations, such as distinct string literals or functional attributes. They constrain both deductions and valid models.
Bridge assumption
An explicit dependency accepting quoted or externally supported content as a premise. Attribution alone does not establish truth.
Checked spine
The formal commitments of a document, with other source material retained and labelled. An aspiration for whole-document coverage, not a claim that all prose is a theorem.
Claim graph / leaf
A network of deductions with evidence at each edge. An unproved leaf is an assumption that remains attached to dependent conclusions.
Closure / closure induction
Reachability along a relation; and the rule that a property holding at the start and preserved by each step holds along every reachable path.
Compare oracle
A budgeted procedure seeking proofs of equivalence or a distinguishing model. It may return unknown; “oracle” does not imply infallible answers without evidence.
Conservativity
An extension preserves old meanings and does not create new consequences between old claims without additional assumptions.
Corpus prior
A proposed removable annotation describing frequencies in a named corpus. It does not establish author intent, choose a reading or affect certification.
Countermodel
A valid situation where all premises hold and the conclusion fails. It proves non-entailment, not necessarily that the conclusion is false in the real world.
DRI / worktree
The directly responsible individual owns decisions and follow-through. A Git worktree gives a worker a separate checkout while sharing the repository’s history.
Elaboration / faithfulness
Translating a convenient construction into a checked language, and preserving its independently specified meaning. A faithfulness proof for that translation is distinct from judging fidelity to an English source.
Entailment / soundness
Entailment means the conclusion holds in every allowed model of the premises. Soundness means an accepted certificate really establishes that relationship.
Environment / meaning identity
Version-bound identifiers for semantic declarations and structured claims. They bind the chosen formal content, not the truth of its descriptions or its faithfulness to intent.
First-order logic
Statements about individual objects, properties and relations using “every”, “some” and logical connections. The base VE fragment is typed and function-free; separate profiles add supported features.
Fidelity gate
A predeclared test of whether an authoring tool preserves source commitments. It is separate from checking whether a proof of the resulting claim is valid.
Invariant / separating certificate
A property preserved by every step; for example, membership in a closed set containing an access source and excluding its target.
Lean
A proof assistant whose kernel checks VE’s mathematical proofs. Its reference theorems do not automatically verify every surrounding implementation.
Mandatory proof
Accept only claims derived by checked evidence from reviewed foundations. Unsupported or unaffordable claims remain unresolved.
N-ary relation
A relation with an ordered list of participants, such as sender, report and recipient. The stage-one branch supports up to six positions.
Narrowing
An attributed choice of some source readings for a particular interpretation, with reasons. It leaves the source set intact and labels dependent results.
Norm
A rule about what is required, prohibited or permitted, possibly with declared exceptions and priorities.
Open term / open texture
A term whose application can require a decision, such as “reasonable”. Its schema records the deciding role, constraints, precedents and version.
Predicate / sort
A property or relation; and a declared kind of object. Sorts can be empty unless the declarations or premises require an inhabitant.
Profile / route
A versioned package of semantics and checks; and the admitted path through parsing, elaboration and a compatible checker. Unsupported combinations reject.
Proof certificate / tableau
A replayable record of proof steps; VE’s base tableau method checks that assuming the premises and denying the conclusion leads to contradiction on every branch.
Proof-carrying action
A proposed exact action accompanied by checked policy evidence and an enforcement mechanism binding that evidence to execution. A research direction here.
Reading set
The versioned interpretations considered so far for a source unit. Each member is unambiguous VE; ambiguity is recorded at the source level.
Residual
The remaining open terms, assumptions, bridge dependencies and unresolved readings. The headline measure of unfinished review, not a universal coverage percentage.
Scalable oversight
Supervising work whose production may exceed the overseer’s own capabilities. Certificates help only where the evidence and remaining review are affordable.
Unknown / completeness
Unknown means no supported answer was established within budget. Logical completeness asks whether every valid entailment has an accepted proof; timely search and successful authoring are further requirements.
Vacuity
A deduction can hold because its premises are impossible or inconsistent. Report that separately instead of treating its proof as useful evidence.
Zero-training English
The requirement that an English speaker can read and write through ordinary prose and English clarification, without learning notation. A design requirement still awaiting human evaluation.
